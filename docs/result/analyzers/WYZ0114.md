# WYZ0114: Use ValueOr instead of a Match that returns the value or a fallback

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

A `Match` on a `Result<T>` that returns the value for a success, and a fallback that does not depend on the error for a failure:

```csharp
var count = result.Match(value => value, _ => 0);
```

## Why it matters

`ValueOr` is that sentence: the value, or this instead.

## How to fix

```csharp
var count = result.ValueOr(0);
```

## What is left alone

- A fallback that costs something or can change something: a call, an allocation, a property. `Match` evaluates the fallback only for a
  failure, and `ValueOr` always does, so the rule reports a fallback only when it is a constant, a local, a parameter or a field.
- A failure delegate that reads the error, a success delegate that does something to the value, `Match` with a result type that differs from the
  type of the value, and a `Match` on a `Task` or `ValueTask`.

## Code fix

Yes. The fix renames the call and keeps the fallback as the one argument, and works with "fix all".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0114.severity = warning   # or none
```
