# WYZ0106: Use EnsureNotNull instead of a null check inside Bind

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

A `Bind` that fails for a `null` value and succeeds with the value otherwise:

```csharp
result.Bind(customer => customer is null ? Result.Failure<Customer>(Error.NotFound("No such customer.")) : Result.Success(customer));
```

## Why it matters

`EnsureNotNull` does the same and does one thing more: it turns a `Result<Customer?>` into a `Result<Customer>`, so the compiler knows the value is there.
It works for a reference type and for a nullable value type, and for `is null`, `== null`, `is not null` and `!= null`.

## How to fix

```csharp
result.EnsureNotNull(Error.NotFound("No such customer."));
```

An error that is not a constant, a local or a field is passed as a function (`EnsureNotNull(() => Error.NotFound(...))`), so that it is still created only
when the value is `null`.

## What is left alone

A success branch that does something with the value (`Result.Success(customer.Name)`), and a condition that is not a plain null check of the value.

## Code fix

Yes. The fix rewrites the call as shown, and works with "fix all in document, project or solution".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0106.severity = warning   # or none
```
