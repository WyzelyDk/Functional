# WYZ0101: A Result is not used

| | |
|---|---|
| Category | Usage |
| Default severity | Warning |

## Cause

The `Result`, `Result<T>`, `Task<Result>`, `Task<Result<T>>`, `ValueTask<Result>` or `ValueTask<Result<T>>` returned by an
expression statement is neither assigned nor returned nor inspected:

```csharp
Save(order);                 // returns a Result: a failure would go unnoticed
await SaveAsync(order);      // the awaited Result is thrown away
SaveAsync(order);            // the task is neither awaited nor used
```

## Why it matters

The whole point of a result is that failure is a value that has to be handled. A discarded result turns a failed operation into
silent success.

## How to fix

```csharp
var result = Save(order);
if (result.IsFailure) { /* handle result.GetError() */ }

return Save(order);          // pass it on
Save(order).ThrowIfFailure();   // or leave the railway as an exception
```

When ignoring the outcome is intended, say so:

```csharp
_ = Save(order);
```

## When to suppress

Fire-and-forget calls whose failure is handled elsewhere. Prefer the explicit discard `_ =` over suppressing the rule.

## Code fix

**Discard the result explicitly** turns `Run();` into `_ = Run();` and `await RunAsync();` into `_ = await RunAsync();`.
It only makes the decision to ignore the outcome visible; it does not handle the failure. Prefer to check the result,
return it, or pass it on. Note that discarding a `Task<Result>` that was never awaited (`_ = RunAsync();`) still lets the
operation run unobserved: usually you want `await`.
