# WYZ0118: Use MapError instead of an OrElse that only returns an error

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

An `OrElse` whose function returns an error, or `Result.Failure` of an error, on a `Result` or `Result<T>`, or on a `Task` or `ValueTask` of one:

```csharp
result.OrElse(error => Error.Create("Could not load the order."));
result.OrElse(() => Result.Failure<Order>(Error.NotFound("Order not found.")));
```

## Why it matters

A function that returns an error replaces the error of a failure and leaves a success alone. That is what `MapError` does, without the detour through a result.
It also stops a reader from looking for an alternative that could succeed: `OrElse` promises one, and this one never does.

## How to fix

Use `MapError`. The function returns the error itself, and a function without a parameter gets one that is not used:

```csharp
result.MapError(error => Error.Create("Could not load the order."));
result.MapError(_ => Error.NotFound("Order not found."));
```

## What is left alone

- The function named `replacement`, which returns a value: for a `Result<Error>` that value is an error too, and `OrElse(e => someError)` returns a success.
  The rule looks at the name of the delegate parameter, never at the type of the expression alone.
- An `async` function, a method group, a function with several statements,
  and a function that returns something else: a result, or `Result.Failure` with a message (`Result.Failure<T>("text")`).
- A call that is not written as `receiver.OrElse(...)` without type arguments, for example `ResultExtensions.OrElse(result, ...)`.

When the function returns the error it was given (`error => error`, `error => Result.Failure<T>(error)`), the step does nothing and [WYZ0115](WYZ0115.md)
reports it instead.

## Code fix

Yes. The fix renames the call, gives a function without a parameter the parameter `_`, drops a return type that the lambda states (`Result<T> () => ...`),
and takes the error out of `Result.Failure(...)`. It works with "fix all".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0118.severity = warning   # or none
```
