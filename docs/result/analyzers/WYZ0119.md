# WYZ0119: Use ValueOr instead of a conditional on the state of a result

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

A conditional expression on a `Result<T>` that returns the value of a success and a fallback for a failure:

```csharp
var count = result.IsSuccess ? result.GetValue() : 0;
var name = result.IsFailure ? LoadDefaultName() : result.GetValue();
var label = result.IsSuccess ? result.GetValue() : $"unavailable: {result.GetError().Message}";
```

The result has to be a name, or names joined by dots (`order`, `this.Order`, `holder.Order`), written the same way in the check and in the read.

## Why it matters

`ValueOr` is that sentence: the value, or this instead. It reads the result once, and it cannot read the value of a failure by mistake.

## How to fix

Which form depends on the fallback:

- A fallback that is cheap (a constant, a local, a parameter or a field) and does not read the error is the value itself: `result.ValueOr(0)`.
  `ValueOr(fallback)` evaluates the fallback also for a success, which costs nothing here.
- Any other fallback becomes a function, so that it is still evaluated only for a failure: `result.ValueOr(() => LoadDefaultName())`.
- A fallback that reads `result.GetError()` becomes a function of the error: `result.ValueOr(error => $"unavailable: {error.Message}")`.
  Every `result.GetError()` in it becomes the parameter.

## What is left alone

- A conditional that is not exactly this shape: another result in the value or the fallback,
  a receiver that is a call or an index (`Load().IsSuccess`, `results[0].IsSuccess`),
  a fallback of another type than the value (the conditional would have another type than `ValueOr`), and a conditional on a `Result` without a value.
- A fallback that has to stay lazy and cannot be moved into a function:
  one that awaits, passes something by `ref` or `out`, declares a variable (`out var n`, `is int n`), throws,
  is a target-typed `new()` (which has no type of its own, so `ValueOr(() => new())` is ambiguous), or reads a `ref`, `out` or `in` parameter,
  a `ref` local, a `Span<T>` or another `ref` struct, or the instance of a struct.
- A function is also not suggested when the value is an `object`, a `Delegate`, a delegate type or an expression tree
  (and `dynamic`, to stay on the safe side): a lambda converts to those, so `ValueOr(() => 5)` would pick the overload that takes the value
  and return the function itself.
  The cheap form, `ValueOr(fallback)`, has no function in it and is still suggested.
- A fallback that reads the error when a name `error` is already in scope or used inside the fallback, because the parameter would hide or clash with it.

## Code fix

Yes. The fix replaces the conditional with the call of `ValueOr` in the form above, and works with "fix all".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0119.severity = warning   # or none
```
