# WYZ0102: Check the state of a Result before reading its error or value

| | |
|---|---|
| Category | Usage |
| Default severity | Warning |

## Cause

`GetError()`, `GetValue()` or `ConvertFailure()` is called on a `Result` or `Result<T>` where nothing guarantees the state the call needs:

```csharp
Error error = result.GetError();      // throws InvalidOperationException when the result succeeded
int value = typed.GetValue();         // throws ResultFailedException when the result failed
var other = result.ConvertFailure<string>();   // throws InvalidOperationException when the result succeeded
var first = Compute().GetValue();     // a call result cannot be checked first
```

## Why it matters

A result is a value that can be in one of two states, and each accessor is only meaningful in one of them. Reading the
wrong one throws, which is exactly the kind of failure the result type exists to avoid.

## How to fix

Check the state first. The analyzer recognises these guards for the *same* variable, field or property:

```csharp
if (result.IsFailure)
{
    log.Warn(result.GetError().Message);      // inside the if
}

if (typed.IsFailure)
{
    return;                                   // an earlier if that leaves the block
}

var value = typed.GetValue();

var message = result.IsFailure ? result.GetError().Message : "ok";   // conditional, && and || are understood too

if (typed.TryGetValue(out _)) { var v = typed.GetValue(); }          // TryGetValue / TryGetError count as checks
```

Better still, avoid the accessors: `Match`, `ValueOr`, `TryGetValue`, `TryGetError`, deconstruction and the railway
methods (`Map`, `Bind`, `Tap`, `TapError`) never throw for the wrong state.

## When to suppress

Tests often assert on the error right after asserting `IsFailure`. Lower the severity for test projects:

```ini
[**/*Tests*/**.cs]
dotnet_diagnostic.WYZ0102.severity = none
```

The analysis is syntactic and local: it does not follow a result through another method or a reassignment between the
check and the call. Suppress a single call with `#pragma warning disable WYZ0102` when you know better.

## Code fix

For `GetValue()` in a method that returns a result, **Return the failure when the result failed** inserts a guard clause above the statement:

```csharp
Result<string> Describe(Result<Order> order)
{
    var total = order.GetValue().Total;
    return Result.Success(total.ToString());
}
```

becomes

```csharp
Result<string> Describe(Result<Order> order)
{
    if (order.IsFailure)
    {
        return order.ConvertFailure<string>();
    }

    var total = order.GetValue().Total;
    return Result.Success(total.ToString());
}
```

The guard returns the result itself when it has the type that the method returns, `ConvertFailure<T>()` when the type differs, and
`Result.Failure(result.GetError())` in a method that returns `Result`. It also works in an `async` method that returns a `Task` or `ValueTask` of a
result.

The fix is offered only where an early return cannot change what else the statement does, so the call has to be evaluated first and always:

- the statement is a declaration, an assignment to a name, an expression statement or a `return`, directly in a block, with the call at the start of
  the expression (`var x = r.GetValue().Length;`, `v = r.GetValue();`);
- the receiver is a name or names joined by dots, so that the guard and the call read the same value.

No fix is offered for a call that comes after another call in the same statement (`Compute() + r.GetValue()`), inside an argument, a conditional, `&&`,
`||`, `??` or a lambda, in a method that does not return a result (nothing says what to return), in an expression-bodied member, or for
`GetError()` and `ConvertFailure()`. Those need a failed result, and nothing says what the code should do for a success. Pick the form that
fits there: an `if` on `IsFailure`/`IsSuccess`, `TryGetValue`/`TryGetError`, `ValueOr`, or `Match`.

The fix is not offered for "fix all": each guard makes the later reads of the same result safe, so one is usually enough.
