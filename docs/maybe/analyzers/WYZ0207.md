# WYZ0207: Remove a step that does not change the maybe

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

A step that hands back a maybe that has the same state, the same value and the same type as the one it was called on:

```csharp
line.Map(order => order);
line.Bind(order => Maybe.Some(order));
line.OrElse(() => Maybe.None<Order>());
line.OrElse(() => default(Maybe<Order>));
```

## Why it matters

The call does nothing, and it is a step that a reader has to understand before they can skip it. It often stays behind after a refactoring.
An `OrElse` that offers none as the alternative leaves a none as none and a value as it was.

## How to fix

Remove the call:

```csharp
line
```

## What is left alone

A step whose type changes (`Map<int, object>(x => x)`, `Maybe.Some<object>(x)`, `OrElse(() => Maybe.None<int>())` on a `Maybe<object>`),
a step that does anything else with the value, and an `async` delegate.
For `OrElse` only the function named `alternative` counts, which returns a maybe, not the one named `replacement`, which returns a value.
An alternative that returns `default(Maybe<T>)` is reported like one that returns `Maybe.None<T>()`.
The `default` literal (`OrElse(() => default)`) does not compile, because it fits both forms of `OrElse`.

## Code fix

Yes. The fix replaces the call with the maybe it was called on, and works with "fix all".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0207.severity = warning   # or none
```
