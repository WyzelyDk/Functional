# WYZ0205: Use ValueOr instead of a Match that returns the value or a fallback

| | |
|---|---|
| Category | Design |
| Default severity | Info (a suggestion; it never breaks a build) |

## Cause

A `Match` on a `Maybe<T>`, or on a `Task` or `ValueTask` of one, that returns the value when there is one and a fallback when there is none:

```csharp
var quantity = line.Match(value => value, () => 1);
var label = line.Match(value => value, () => LoadDefaultLabel());
```

## Why it matters

`ValueOr` is that sentence: the value, or this instead.

## How to fix

A fallback that is cheap (a constant, a local, a parameter or a field) becomes the value itself.
Any other fallback stays a function, which `ValueOr` runs only when there is no value, like `Match` does:

```csharp
var quantity = line.ValueOr(1);
var label = line.ValueOr(() => LoadDefaultLabel());
```

A `Task<Maybe<T>>` and a `ValueTask<Maybe<T>>` have no `ValueOr` that takes the value, so they always get the function.

## What is left alone

- A `Match` whose first delegate does something to the value, one whose result type differs from the type of the value (`Match<int, object>`),
  and a delegate that is a method group, is `async`, has several statements or is not a lambda at all.
- A fallback that has to stay a function when a lambda would be taken for the value, or when the function would not bind to the overload that was meant:
  a maybe of `object`, `dynamic`, `Delegate`, `MulticastDelegate`, a delegate type or an expression tree.
  `maybe.ValueOr(() => 5)` on a `Maybe<object>` picks the `ValueOr(T)` that takes a value, and returns the function itself.
  On a `Task` or `ValueTask` of a `Maybe<object>`, a function that returns a `Task<object>` binds to the overload that awaits it.
  A fallback that is cheap is still reported on a plain maybe of these types, because it is passed as it is.
- A fallback that has no type of its own, a `throw` expression or a target-typed `new()`: it converts to every overload of `ValueOr` that takes a function,
  and the compiler reports the call as ambiguous.
- A call that is not written as `receiver.Match(...)`, for example `MaybeExtensions.Match(maybe, ...)`.

The same sentence written as a conditional is [WYZ0203](WYZ0203.md), and a `ValueOr` whose fallback does work is [WYZ0208](WYZ0208.md).

## Code fix

Yes. The fix renames the call and drops the first delegate. A cheap fallback on a plain maybe becomes the argument itself (`ValueOr(1)`, evaluated always);
any other fallback stays the lambda. It works with "fix all".

## When to change the severity

The rule is a suggestion, so it shows up in the editor and not in the build output. Make it louder, or switch it off, in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.WYZ0205.severity = warning   # or none
```
